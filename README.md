# Сервис совместных холстов

Упрощённый бэкенд сервиса, в котором пользователи вместе рисуют на холстах: создают, меняют и удаляют фигуры. Сервис хранит историю изменений и умеет показать состояние холста на любой момент времени.

Стек: Node.js 22, TypeScript, Express 4, Sequelize 6, PostgreSQL 16, Zod 4.

## Запуск

```bash
docker compose up -d      # PostgreSQL 16 на порту 5433 со схемой и тестовыми данными
cp .env.example .env
npm ci
npm run dev               # http://localhost:3000
```

Проверка кода:

```bash
npm run lint
npm run build
```

Чтобы начать с чистой базой, выполните `docker compose down -v && docker compose up -d`.

## API

Access-токен для пользователя из тестовых данных:

```bash
TOKEN=$(npm run -s token -- 1) # 1 - id тестового пользователя
```

Активация аккаунта по токену из письма:

```bash
curl -X POST localhost:3000/api/auth/activate/valid-token # valid-token у carol, stale-token у dave
```

Участники холста:

```bash
curl -H "Authorization: Bearer $TOKEN" \
  "localhost:3000/api/canvas/participants?canvas_id=1&offset=0&limit=10"
```

Состояние фигур холста на момент времени (`shape_id` можно не указывать):

```bash
curl -H "Authorization: Bearer $TOKEN" \
  "localhost:3000/api/canvas/shape/snapshot?canvas_id=1&shape_id=shape-0001&date=2030-01-01T00:00:00Z"
```

Пакетное изменение фигур (`add`, `update`, `delete`). Если действие не удалось, оно попадает в `failed`, а остальные действия пакета всё равно применяются:

```bash
curl -X POST localhost:3000/api/canvas/shape/actions \
  -H "Authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d '{
    "canvas_id": 1,
    "actions": [
      { "operation": "update", "shape_id": "shape-0001", "content": { "type": "sticker", "text": "Готово" } },
      { "operation": "add", "shape_id": "shape-new", "content": { "type": "arrow" }, "rank": 1001 },
      { "operation": "delete", "shape_id": "shape-0002", "version": 1 }
    ]
  }'
```

Замер пакетного изменения (сервер должен быть запущен):

```bash
npm run bench:actions -- 500 1000 2000
```

## Архитектура

### Слои

Поток запроса: роутер → контроллер → сервис → репозиторий → модель.

```
src/
  index.ts                 точка входа
  routers/                 маршруты
  controllers/             разбор и валидация запроса, ответ
  services/                бизнес-логика и транзакции
  repositories/            доступ к БД
  models/                  модели Sequelize
  middlewares/             авторизация, обработка ошибок
  scripts/db.script.ts     подключение к БД и managedTransaction
  utilities/               конфигурация, ошибки, время
db/init.sql                схема и тестовые данные
tools/                     вспомогательные скрипты
```

- **Роутеры** только связывают путь с методом контроллера. Асинхронные обработчики оборачиваются в `asynchronousMW`, который передаёт ошибку в обработчик ошибок Express.
- **Контроллеры** валидируют query и тело Zod-схемами через `validateQuery` и `validateBody` из `controllers/common/request.utils.ts`, берут пользователя из `req.token` и формируют ответ.
- **Сервисы** содержат бизнес-логику: проверку доступа, сценарии и границы транзакций. Сервисы экспортируются как синглтоны.
- **Репозитории** — единственный слой, который обращается к БД: через модели Sequelize или сырым SQL через `GLOBAL_DB_MANAGER.connection.query`. Ошибку БД репозиторий оборачивает в `ErrorExtended.App.DB.FailedCRUD`.
- **Модели** описывают таблицы для Sequelize. Схему БД создаёт `db/init.sql`, а не синхронизация моделей.

### Ошибки

Все прикладные ошибки — наследники `ErrorApp` (`utilities/exceptions/`), их создают фабрики `ErrorExtended.*`. У каждой ошибки есть HTTP-статус и машинный `code`. Обработчик `errorMW` превращает `ErrorApp` в ответ `{ code, message, fields }`, а любую другую ошибку — в 500 `INTERNAL`.

### Транзакции

`GLOBAL_DB_MANAGER.managedTransaction(callback, options?)` открывает транзакцию, коммитит её после успешного колбэка и откатывает, если колбэк бросил ошибку. Если в `options.transaction` передана родительская транзакция, колбэк выполняется во вложенной транзакции (SAVEPOINT). Транзакция передаётся в репозитории явно, последним параметром.

### Предметная область

| Таблица                  | Что хранит                                                                |
| ------------------------ | ------------------------------------------------------------------------- |
| `wb_users`               | пользователи; флаги `is_activated`, `is_blocked`                          |
| `wb_user_emails`         | почтовые адреса пользователя; флаг `is_confirmed`                         |
| `wb_confirmations`       | одноразовые токены из писем (активация аккаунта и др.) со сроком действия |
| `wb_refresh_tokens`      | refresh-токены открытых сессий                                            |
| `wb_canvases`            | холсты; `version` — счётчик изменений холста                              |
| `wb_canvas_participants` | участники холста с ролью `owner`, `editor` или `viewer`                   |
| `wb_shapes`              | текущее состояние фигур; удаление мягкое (`is_deleted`)                   |
| `wb_shape_history`       | журнал изменений фигур, только добавление записей                         |

### Аутентификация и активация

- Доступ к API холстов идёт по access-токену (JWT) в заголовке `Authorization: Bearer …`. Его проверяет `authMW` и кладёт полезную нагрузку в `req.token`.
- Активация аккаунта: пользователь переходит по ссылке из письма с одноразовым токеном. Сервис находит подтверждение, подтверждает почтовый адрес, помечает пользователя активированным, удаляет подтверждение и открывает сессию: выпускает access- и refresh-токены и сохраняет refresh-токен.

### Фигуры, версии и история

- Читать холст (участники, снимок) может любой его участник, изменять фигуры — только `owner` и `editor`.
- Каждое изменение фигуры (`add`, `update`, `delete`) увеличивает версию холста (у новой фигуры версия 1, `update` и `delete` её увеличивают) и записывает состояние фигуры в `wb_shape_history` вместе с новой версией холста (`canvas_version`).
- Пакет действий выполняется в одной транзакции, каждое действие — во вложенной. Неудачное действие откатывается отдельно и попадает в `failed`, остальные применяются.
- Для оптимистичной блокировки действие может передать `version`. Если версия фигуры в БД отличается, действие получает ошибку конфликта версий.
- Снимок на момент времени собирается из истории: по дате находится версия холста на тот момент, затем для каждой фигуры берётся последняя запись не позже этой версии.
- После изменения пакета контроллер отправляет события во внешний сервис продуктовых метрик (`ServiceMetric`). В тестовом окружении сетевой вызов эмулируется задержкой `METRIC_LATENCY_MS`.

### Прочее

- Конфигурация читается из переменных окружения и валидируется Zod-схемой в `utilities/config.ts`. Пример значений лежит в `.env.example`.
- Текущее время берётся из БД (`DateTimeProps.now()`), чтобы не зависеть от часов сервера приложения.
